ROOT CAUSE

The form wrapped the useFormState action in an inline
async function with router.push:

  <form action={async (fd) => {
    const result = await formAction(fd);
    if (result?.id) {
      router.push(`/w/${workspaceSlug}/projects/${result.id}`);
    }
  }}>

This LOOKS right, but it's unreliable in Next.js 14 App
Router for two reasons:

  1. The wrapper is NOT the form's transition. React's
     form transition machinery sees a custom action prop,
     not the formAction from useFormState, so the pending
     state and the post-action state update can desync.

  2. router.push is client-side navigation. The transition
     might still be settling, and the navigation can fire
     before the form's optimistic UI has fully unmounted.
     On a fast machine the navigation completes; on a
     slow connection (or while the geocoder is doing
     background work) the form just sits there until
     the user gives up and hits refresh.

FIX

Switched to the canonical Next.js 14 pattern: do the
navigation SERVER-SIDE.

  lib/projects/actions.ts:
    - Added `import { redirect } from 'next/navigation'`
    - In createProjectAction, after the project is
      created and revalidatePath is called:
        redirect(`/w/${workspaceSlug}/projects/${project.id}`);
    - Throws a NEXT_REDIRECT signal that the form's
      transition handles natively. No client-side
      router.push needed.

  app/(app)/w/[workspace]/projects/new/NewProjectForm.tsx:
    - Removed the `useRouter` import
    - Changed the form's `action` to just be
      `action={formAction}` (the bound server action
      directly, no wrapper)
    - The returned state is now only used for field
      error rendering (the success case redirects
      before the state update is even read)

Why server-side redirect is more reliable:
  - The redirect is part of the action's HTTP response.
    The browser navigates as part of the form submission,
    not as a separate client-side transition.
  - Works even if the form is unmounted mid-transition
    (e.g., React Strict Mode double-invoke).
  - Works in slow networks because the navigation is
    "baked in" to the response — the browser doesn't
    have to wait for the React tree to settle.
  - Preserves the URL the user lands on (no flicker,
    no client-side history-entry shenanigans).
