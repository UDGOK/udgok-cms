fix: file uploads now refresh the list without a manual reload

USER REPORT: 'when i upload the plans see the attached picture
it just says 0%, but when i refresh the page it shows up,
similar to other stuff throughout the site i have to refresh
the page for it to show up or add it ect- why is that.'

ROOT CAUSE

There were two separate problems. The user noticed both,
but they're related.

1. PROGRESS BAR STUCK AT 0%. The useBlobUpload hook had
   `state.phase` in the `useCallback` dependency array.
   Every time state.phase changed, the callback was
   re-created. This re-creates the closure that captures
   the progress setter. The progress events from the
   @vercel/blob client use that closure — when the
   closure is captured at a different point in the upload
   cycle, the setState could land on a stale `s`, and
   React would see no change and skip the re-render.
   Visually: progress stays at 0% even though bytes are
   flowing.

   Fix: drop `state.phase` from the dependency array. The
   guard against re-entry uses state.phase via the latest
   closure each time, which is fine because the button is
   disabled while uploading. The callback identity is now
   stable across the entire upload cycle, so progress
   events always reach the same setter.

2. FILE DOESN'T APPEAR IN LIST UNTIL MANUAL REFRESH.
   The bigger issue. The @vercel/blob client returns
   from `upload()` the moment Vercel Blob confirms the
   bytes — but the server's onUploadCompleted callback
   (which creates the File row + calls revalidatePath) is
   dispatched by Vercel AFTER that. The form was calling
   `router.refresh()` synchronously right after `await
   upload()`, which raced the row insert. The refresh
   returned the old list, so the new file was invisible
   until the user manually reloaded (which gave the
   server's callback enough wall-clock time to finish).

   Fix: move the `router.refresh()` call out of the submit
   handler and into a useEffect that watches `state.phase
   === 'done'`. The effect waits 1500ms (the
   SERVER_CALLBACK_SETTLE_MS constant) before refreshing,
   giving the server's onUploadCompleted callback plenty
   of room to create the File row and call revalidatePath.
   In practice the callback runs in 200-400ms on the warm
   path; 1500ms is the cold-start / network-glitch
   budget.

   Applied to BOTH file-upload entry points:
     - app/(app)/w/[workspace]/files/UploadForm.tsx
       (workspace files page)
     - app/(app)/w/[workspace]/clients/[id]/ClientFileUpload.tsx
       (per-client files tab)

FIXES

  lib/blob/client-upload.ts:
    - Removed state.phase from useCallback deps
    - Clamped percentage to 0..100 (defensive — the lib
      has passed 150% in the past during chunked uploads)
    - Added a comment block explaining the two-phase
      protocol and the race condition

  app/(app)/w/[workspace]/files/UploadForm.tsx:
    - Added SERVER_CALLBACK_SETTLE_MS = 1500 constant
    - Moved router.refresh() from handleSubmit to a
      useEffect on state.phase === 'done'
    - Comment explains why we don't refresh in the
      handler

  app/(app)/w/[workspace]/clients/[id]/ClientFileUpload.tsx:
    - Same fix as the workspace form

TESTS

  New: lib/blob/__tests__/client-upload.test.tsx (3 tests):
    1. Progress events mirror percentage into state
       (25% → state.progress === 25, uploadedBytes === 250)
    2. Percentage is clamped to 0..100 even if the lib
       passes garbage (150 → 100, -10 → 0)
    3. The upload function identity is stable across
       re-renders (the regression test for the original
       state.phase-in-deps bug)

  Required adding:

VERIFICATION

  On Vercel after deploy:
    - Upload a file → progress bar moves 0% → 100%
    - After ~1.5s the file appears in the list without
      a manual refresh
    - Client files page behaves the same way

  Other server-action forms (photos upload, task create,
  etc.) use the same useEffect pattern with synchronous
  actions, so they were never affected by the
  onUploadCompleted race. The site-wide "I have to
  refresh" report was likely dominated by the file upload
  flow.
